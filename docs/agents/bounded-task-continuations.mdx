---
title: Bounded task continuations
---

Company alert-only monitoring continues to suppress general observation, repair,
watchdog and repeated blocker wakes. An explicitly owned background job may use
`set_task_monitor` with `kind: "task_continuation"` to read its result once without
changing the company's monitoring policy.

Include a stable job/candidate/stage identity in `externalRef`, a `serviceName`, a
`timeoutAt`, and a finite cumulative `maxAttempts`. Use the existing task, plan,
session, candidate and evidence. The native scheduler claims the check once and
uses its durable task-and-schedule wake key; repeated scheduler ticks do not
repeat it. Active executions, assignment, approval, quota, budget and independent
review guards continue to apply. The continuation is permission to read and
report the job's terminal result, not permission to repeat a proof or failed job.

Await the owned executor's terminal event when available. Otherwise schedule one
bounded result check after the expected finish. If work is still running, retain
the same job and report its state; never create a new execution or reset attempt
counters to obtain another check. Missing job identity, deadline or attempt bound
fails validation and cannot bypass alert-only monitoring. Existing
`external_service` monitors retain their prior behavior.

## Review and approval handoffs

When a queued assignment is superseded by another assignee before execution
starts, cancellation also settles its pending handoff through the existing execution-release service.
An already-saved review or approval request can then proceed without an extra
comment, timer or provider retry. The cancelled assignment does not execute.

Promotion rechecks current ownership, task and stage eligibility, process cleanup,
pauses, budgets and access. Existing holds and operator Stop cancellation
semantics remain in force. It uses the existing
durable wake receipt and does not reset review or continuation counters, change
sessions, accept a stage, or repeat completed tests. Reconciliation and response
wait cancellations do not use this promotion path.

The cancellation transaction notifies the existing deferred-receipt worker. It
also reconstructs saved requests for the current review or approval participant
at startup. Failed delivery retains the same receipt and uses the shared worker's
retry deadline. Stale stage requests and paused participants are not selected.
After settlement the worker becomes quiet; no additional polling is introduced.

### Temporary pause and unstarted stage requests

A temporary company or agent pause preserves a never-started request for the
current review or approval stage, including when it already waits on another
execution guard. Resume delivers that same request through normal admission.
An explicit task/run Stop retains its cancellation semantics.

For an older release that already cancelled such a request during lifecycle
Stop, the existing startup/resume recovery event may record one new request for
the still-current stage. It requires an active company, ready participant, a
run-less lifecycle-cancelled assignment receipt, an explicit native pause-journal
marker at cancellation, no termination in that original obligation window, no
later receipt or invocation, no live or completed stage delivery, and no previous
reconstruction key. Missing or ambiguous pause evidence stays held. An active pause on the task or
an ancestor leaves the reconstruction key unused until that hold is released. The issue lock and
persistent stage/participant key deduplicate concurrent recovery. The original
cancelled receipt stays unchanged; completed worker work, provider history,
planning context, reviews and decision counters are not rewritten. A provider
failure or deliberate operator Stop is not an unstarted request.

The saved-receipt worker rechecks execution authority and all existing guards.
This recovery adds no scheduler or periodic scan and cannot repeat itself after
its replacement request is cancelled.

### Stop requests recorded before provider dispatch

A sealed legacy preparation can contain a pending Stop request without a
provider acknowledgement. Physical cleanup may use the existing preparation
proof only when that receipt contains exactly `state: requested` and a valid
`requestedAt` within the run's start and finish times. The earlier-controller,
complete non-execution journal, built-in adapter, no-output, process and
environment cleanup checks still apply. Contradictory or incomplete evidence
keeps the hold.

This proof does not write an acknowledgement, resume the cancelled task, remove
its recovery hold or change its saved provider session or planning context.
