title: Bind native review to a source candidate
description: Optional candidate SHA on the existing native task review API, with isolated Bruno examples.
---

`PATCH /api/issues/:id` accepts an optional `reviewRequest.candidateSha`
alongside the existing required `reviewRequest.instructions`. This adds a field
to the native task API; it creates no new route or review workflow.

This is a schema example, not permission to mutate a live task. The disposable
fixture below is the only environment described here.

```json
{
  "status": "in_review",
  "comment": "Review the exact candidate and its complete diff and evidence.",
  "reviewRequest": {
    "instructions": "Review the full candidate against the agreed base.",
    "candidateSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}
```

The example SHA is a placeholder; use the full actual candidate commit. The
optional field must match `^[a-f0-9]{40}$`: exactly 40 lowercase hexadecimal
characters. Branch names, abbreviated SHAs, uppercase text and JSON null are
invalid. Malformed values return HTTP 400 with the validation path
`reviewRequest.candidateSha`. Normal authorization, company access, checkout,
review-stage transition and audit rules still apply. Do not send assignee or
execution-stage overrides.

For a configured bound task, the server captures clean final HEAD under the
writer's task, run and workspace leases in the same transaction as the review
transition. Omitting `candidateSha` allows that server capture; supplying it only
narrows capture and returns a conflict if it differs from observed HEAD. A client
SHA never creates a trusted receipt. Board/user transitions without an eligible
writer run refuse with `writer_missing`; they cannot manufacture writer authority.

The server persists `executionState.sourceReviewCapture` and
`executionState.reviewRequest.candidateSha`. Heartbeat derives `reviewCandidateSha`
only for the assigned pending reviewer and matching task/workspace/binding/stage.
Consecutive review stages carry the original receipt and candidate forward when
no writer handoff occurred; they do not recapture reviewer-time HEAD. A return to
the writer requires a fresh writer-owned capture on its next review handoff.
A configured bound review without a matching receipt fails closed. This is source
identity, never permission to execute, accept work or activate indexing.

Capture is owned by `server/src/services/workspace-source-inspection.ts` and
`source-review-handoff.ts`; persistence by `issues.ts`. The request contract lives
in `packages/shared/src/validators/issue.ts` and `types/issue.ts`; heartbeat consumes
it through `server/src/services/heartbeat/source-memory-run-state.ts`.

## Compatibility and mixed-version order

Existing requests with only `reviewRequest.instructions` remain valid at the API
schema level. For configured bound tasks they use server capture under the same writer leases;
otherwise they do not acquire current-source evidence standing. Old saved results and sessions
remain intact; never infer a candidate from a branch, baseRef or arbitrary context.

Upgrade the server schema and native candidate producer before clients send the
new field. A server without this strict-schema addition rejects the unknown
property. Until then, use only the supported `reviewRequest.instructions` and
include the full candidate SHA, whole-diff link and evidence links there. This
text supports manual review; it does not implement the new typed source binding.
Never resend a rejected mutation automatically.

Keep indexing disabled during an approved cutover, quiesce older workers and drain
their transactions before compatible workers touch retained provenance. Older
pruning workers are not safe rollback targets for retained ledgers. These examples
authorize no deployment, retention migration, deletion or real indexing.

## Disposable fixture collection

`bruno/source-review-candidate/` is a standalone collection with valid and invalid
requests plus readback. Open that directory as the collection, rather than running
all parent collections. Provision a disposable local instance and fresh synthetic
company/task with a native review stage and a never-executed synthetic participant.
Use no production data, credentials, remote provider access or shared state.

Before creating fixture entities, an authorized fixture operator must start the
existing task drain (`POST /api/instance/task-drain`), confirm it with GET, keep it
active through the fixture, pause the synthetic company, and disable execution.
The collection does not provision entities or start/extend drains. A drain's POST
receipt is not the computed GET status. Verify zero adapter invocations/running
runs separately, then stop the fixture server and clean up its isolated database.
Never drain a real operator instance for this fixture.

Inject these values into the Bruno process without committing an environment file:

| Process variable | Purpose |
| --- | --- |
| `PAPERCLIP_FIXTURE_BASE_URL` | Disposable HTTP loopback origin, with its isolated port |
| `PAPERCLIP_FIXTURE_ISOLATED` | Explicit `true` confirmation of fixture isolation |
| `PAPERCLIP_FIXTURE_COMPANY_ID` | Fresh paused synthetic company |
| `PAPERCLIP_FIXTURE_ISSUE_ID` | Its synthetic task with native review policy |
| `PAPERCLIP_FIXTURE_CANDIDATE_SHA` | Full candidate commit to persist and read back |
| `PAPERCLIP_FIXTURE_TOKEN` | Optional injected fixture credential; omit only for an isolated local-trusted fixture |

Run requests 01–05 once in order. Read active drain and paused company immediately
before mutation; in-memory checks expire after 30 seconds. Expected responses are
GET 200, GET 200, malformed PATCH 400, valid PATCH 200, and persisted GET 200.
The valid mutation must leave a pending review stage retaining the exact SHA.
The guards reduce accidental use; they do not prove isolation or prevent a drain
expiry race. Fixture isolation, a never-executed participant and operator cleanup
remain essential. Stop on failure; no retry or polling loop is supplied.

The collection injects a credential header using `bru.getProcessEnv` and keeps
runtime state only with `bru.setVar`. It has no token environment file, credential
logging, or persistence calls. In Bruno v4, environment/global mutation scripts
persist changes; keep secrets in process injection or supported secret-manager
references, never `bru.setEnvVar` or global/environment setters. See the
[Bruno v4 release guidance](https://www.usebruno.com/v4-release) and
[official JavaScript reference](https://github.com/usebruno/bruno-docs/blob/main/testing/script/javascript-reference.mdx).

## Evidence scope

Actual isolated curl evidence establishes malformed-field rejection, successful
persistence/readback and producer binding from saved native review state, with
zero adapter invocations and cleanup. The reusable Bruno files document those
requests; Bruno runner execution is not claimed. Documentation additions do not
repeat the curl fixture, semantic compiler, Postgres, synthetic or CI checks.
Hosted CI, full Rust rebuild, full UI qualification and live provider dispatch
are separate from this source/API fixture evidence.

### Native Runner attribution

Fresh native Runner tasks use the final selected provider and model after task
overrides, defaults and compatibility selection
when no legacy phase-routing profile exists. The task work mode determines
planning or implementation; a pending review assigned to the current participant determines review, even
when its capture is missing or invalid (which holds the review). Phase-routed tasks retain their selected profile.
This attribution grants no task or repository access. Restart recovery retains
its existing refusal for an unverified old source snapshot, preserves the saved
session and context, and never substitutes a newly edited live model for it.

An interaction-only native review does not itself produce a writer capture. On a
bound source workspace it therefore refuses with `source_memory_review_candidate_missing`
before any source read; artifact-only review workspaces should stay unbound.
Setting the source-memory config does not opt every project in. Projects without
a matching company/project binding, including projectless artifact reports,
keep the feature-off completion behavior: optional submitted source citations
and claimed verification fields are discarded without failing ordinary work.
An opted-in project still refuses submitted evidence when its persisted workspace
is missing or its repository does not match. A recovering bound review still
requires a verified saved source snapshot. None of these checks creates a wake,
changes a session, or overrides a task dependency.
Native preparation may ensure an idempotent completion contract and materialize
response inputs before source validation. Neither starts a provider or accepts
work. Model-fallback warnings are published only after source validation succeeds.

Source verification flags are owned by the control plane. Provider-supplied
`sourceCitationResults` and `sourceCurrentEvidenceSatisfied` are removed from
native finalization envelopes and diagnostic result snapshots as well as
canonical completion results. Verified run evidence remains separate from the
provider's report; ordinary result fields and submitted citations are preserved.


The adapter envelope is diagnostic, not a replay key. Native completion replay
uses the canonical result and hash persisted by the control-plane port, which
strips these two keys before computing that hash. Restart settlement and the
native finalizer read the accepted canonical row; they do not compare the
adapter envelope with an older raw snapshot. Stripping the diagnostic clone
therefore preserves canonical replay identity and saved provider sessions.


## Aggregate capacity and cursor continuation

A binding can optionally set `maxContentBytes` to a positive safe integer. Without the optional top-level `capacity` policy below, omission retains the existing 128 MiB reader default. With that policy, the default is sized from memory and disk and can exceed 128 MiB. This setting requires the capacity-capable manifest pinned by the server; the original accepted reader remains supported for configurations without this option. Manifest hashes, reader revisions and all 38 code-file hashes are verified before execution. Capacity is operator configuration, never source-code instructions.

Aggregate content capacity is separate from file eligibility, per-file limits, ledger disk usage and RAM. Adjusting aggregate capacity preserves the saved immutable revision, file plan, committed cursor and cached blobs. Subsequent manifests record the effective configured content budget. Changed filtering limits still reject an existing plan, and reducing capacity below already indexed bytes rejects even an unchanged index. No state is deleted or silently restarted.

Without the optional `capacity` policy, a worker deadline bounds one operation, not repository size. Operators must retain the task, scope, frozen revision and plan and verify cursor progress before admitting another continuation; there is no background continuation scheduler. With `capacity`, the completion-driven continuation loop below handles this within one bounded native preparation. Completed blobs stay cached. The operator must stop on a non-advancing cursor, changed identity, cleanup failure, unsupported reader, exhausted configured resource capacity or missing authority, and must not wake a provider merely to poll indexing. Native dependency/review handoffs wait for an actual complete report.

The additional real-worker capacity release test requires `PAPERCLIP_SOURCE_CAPACITY_FIXTURES` to name a JSON file with `legacy` and `capacity` reader entries containing `root`, `manifest`, `manifestSha256` and `revision`. Both code-only readers must match the server pins; missing fixtures fail the test. This gate exercises manifest selection, old-reader refusal with a configured budget, constructor budget forwarding and actual facts provenance without providers or production data.


Without the `capacity` policy, ledger disk capacity is an independent operator gate: measure the entire scoped state directory, including SQLite WAL/SHM files, before admitting a continuation and after each operation. Enforce the configured per-repository and total state limits and check available disk and process memory; an aggregate content limit alone does not bound SQLite storage. A ledger-capacity failure stops further continuation and handoff. The reader itself does not enforce a filesystem quota. `source_memory_index_budget` and `source_memory_manifest_changed` distinguish reader capacity and saved-plan failures from a generic worker failure.

These Node release gates are excluded from ordinary Vitest discovery: `server/vitest.config.ts` includes only `src/**/*.test.ts` and `scripts/**/*.test.mjs`, while the gates live in `src/services/*.test.mjs`. The root config delegates server discovery to that project configuration. Run the config gate explicitly with `node --test server/src/services/source-memory-capacity-config.test.mjs`, and the worker gate with `PAPERCLIP_SOURCE_CAPACITY_FIXTURES=/absolute/fixtures.json node --test server/src/services/source-memory-capacity-worker.test.mjs`.

The exact reusable reader delta is retained in `docs/guides/source-reader-capacity.patch`, including the five real Git/SQLite regression tests and source provenance. Apply it to the exact accepted code-only reader baseline described there; runtime code remains covered by the new 38-file manifest pin.

## Resource-aware indexing and saved-progress continuation

An optional `capacity` object in the operator source-memory JSON configuration
provides resource-aware storage allowances for native preparation. It does not
change the independent limits of external operator scripts. With
no `capacity` object the existing behavior is unchanged. This is infrastructure
configuration, never a task-prompt setting; only explicitly bound projects use it.
It requires the existing capacity reader `d09c6d2da901d5201b58deebd040725ba926737c`.

```json
{
  "capacity": {
    "mode": "auto",
    "diskFraction": 0.1,
    "reserveDiskBytes": 1073741824,
    "memoryFraction": 0.2,
    "retrievalExpansionFactor": 16,
    "reserveMemoryBytes": 268435456,
    "maxBatchFiles": 100,
    "sliceMs": 60000,
    "maxSlices": 32,
    "maxDurationMs": 600000
  }
}
```

This fragment belongs beside `version`, `state`, `reader`, `manifest`, and
`bindings` in the existing configuration. It does not enable a new project or
change any model, provider, agent session, task policy, or approval. Existing
per-binding `maxContentBytes` remains an explicit content ceiling.

Automatic mode allocates up to 10% of filesystem capacity, constrained by current
free disk after the 1 GiB reserve. The share stays fixed as usage grows; repeated
batches cannot ratchet the allowance upward. Optional `maxStateBytes` and
`maxScopeBytes` impose explicit ceilings that automatic sizing cannot increase.
Fixed mode requires both ceilings. Sizes are bytes. Storage is measured on disk,
including SQLite sidecars; it is independent of RAM. The disk-derived content allowance
is a quarter of the scope storage allowance. Full document retrieval also needs
memory: content is capped at the usable memory share divided by
`retrievalExpansionFactor` (default 16, configurable integer 1–64). Explicit
content ceilings can lower this further. If committed content exceeds a newly
smaller resource allowance, the request stops with saved progress intact; it does
not evict source or repeatedly retry.

Available memory is the lesser of host free memory and Node's process-available
memory (which accounts for supported container limits). After the memory reserve,
20% is usable for batches. Each batch reserves a conservative 16-times per-file
expansion plus disk overhead. Disk and memory are resampled between batches.
Complete `verify` and existing-event `commit` skip allocation probes and never
fail merely because another scope exceeded its disk allowance. A phase that
materializes full documents still checks memory, but not shared growth allowance.
These are admission safeguards, not hard OS memory quotas or exact predictions of
SQLite expansion. Limits are checked again after each batch; an external writer
or disk consumption outside Paperclip can still cause a resource failure. The additional content ceiling accounts for the existing full-document
retrieval path; its 16-times expansion allowance is still a conservative estimate,
not an OS-enforced maximum. On systems whose free-memory reading excludes
reclaimable pages, operators can lower the reserve and the expansion factor after
measuring actual retrieval cost; this explicitly reduces the safety margin.

The private SQLite capacity lease serializes index growth across configured
companies/scopes sharing this state directory. Complete unchanged scopes and
pre-dispatch verification do not take the global lease; the existing per-scope
runtime lock still applies. The growth lease is released before document retrieval
and runtime observation writes. Growth contention refuses immediately
with `source_memory_capacity_busy`; no polling or hidden retry is started. SQLite
releases the lease on process exit, including a crash. External tools and legacy
configurations without this policy must not concurrently write the same state.
The configured `state` root must be private (mode 0700) and must not itself be a
symlink; enabling capacity on an incompatible existing root refuses with a named
state error. The feature does not rewrite existing directory permissions. State
inventories refuse symlinks and special files, skip vanished journal entries,
and are capped at 20,000 entries.

Each worker commits reader batches to the existing manifest and blob cache. At
the soft slice deadline it yields its revision, immutable plan identity and saved
cursor. The parent continues immediately only after strictly increasing progress
on the same plan. Completed files and cached blobs are reused, and the total blob
read count includes every slice. A completed unchanged revision takes the normal
zero-blob-read path. Restarting the request resumes the same durable reader state;
no new ledger, file-plan reset, or synthetic successful runtime observation is
created for an unfinished slice.

The 180-second process watchdog remains unchanged. `sliceMs` is 1–120,000 ms,
`maxSlices` is 1–128, `maxBatchFiles` is 1–500, and `maxDurationMs` is
1–3,600,000 ms. The overall invocation deadline also cancels an active child.
Defaults are 60 seconds / 32 slices / 100 files / 10 minutes. The current batch
may overrun the soft deadline; the watchdog and cancellation still apply. No
resource refusal, reader exception, aborted operation, changed source/plan, or
non-advancing cursor is automatically retried. Budget exhaustion is named
`source_memory_continuation_budget`; insufficient resources use
`source_memory_capacity_wait`. Saved progress remains for the next authorized
preparation after capacity/configuration changes. There is no timer, provider wake,
new agent turn, or scheduler that repeatedly probes for capacity.

Validation: use `source-memory-autosize.test.mjs` with the pinned-reader fixture
configuration. It exercises disposable Git repositories, real SQLite manifests,
separate parent/worker processes, saved-progress restart, byte-identical cache
reuse, zero-read duplicates, contention, resource refusal and no-progress stops.
It does not index company source or run a model as a fixture.

```sh

node --experimental-vm-modules --test server/src/services/heartbeat/source-memory-admission.test.mjs
```

## Share existing indices as development references

Current-candidate evidence and historical development references have separate
purposes. Opting an ordinary delivery project into strict source review solely
to read another project's index can block its legacy reviews. Keep the existing
`bindings` and their candidate gates unchanged. An operator can instead add
`references` to the same private source-memory configuration:

```json
{
  "references": [
    {
      "companyId": "company-id",
      "consumerProjectId": "delivery-project-id",
      "projectId": "indexed-source-project-id",
      "repositoryId": "github.com/example/application",
      "revision": "0123456789012345678901234567890123456789"
    }
  ]
}
```

This is an additive configuration fragment. Keep the configured reader, state,
capacity policy and source-project bindings. The referenced project must have
one matching binding in the same company and an already complete index at the
explicit full revision. References are opt-in per consuming project. Removing
a share before its lookup finishes discards the returned snippets. An unreadable
or invalid configuration does not opt a consumer into reference preparation. Missing,
busy, corrupt or incomplete reference indices report `unavailable` when no
reference is delivered, or `partial` when other targets still supply snippets. They do
not rebuild the index, retry, wake agents or impose a new review requirement.
Run cancellation and lost execution ownership still stop preparation normally.

Native task prompts receive a bounded **Indexed repository references** section
during planning, implementation and review. The native preparation branch owns
this optional integration. Legacy adapter preparation and compact resume
markdown stay unchanged. The lookup reads the
existing SQLite documents in a guarded subprocess; it performs no Git blob
reads, index refresh or source-plan rewrite. It selects at most four reference
targets and two snippets per target, with a six-second shared deadline. The
injected section is bounded to 24 KiB, including metadata. Search first ranks
matching paths; only a path miss scans indexed document text. Caseful Unicode
uses Unicode folding. Search is lexical, not semantic, and coverage/exclusions
remain those of the indexed revision. A successful empty lookup reports
`no_matches`. No-match scans can take longer than path matches; the shared
subprocess deadline makes this optional work bounded.

Each snippet names its indexed scope, revision, path, line range and full-file
content hash. These are historical, untrusted references for locating relevant
code. Inspect the actual task workspace and changes before implementation or
review. Reference snippets cannot populate `sourceCitations`,
`sourceCitationResults` or `sourceCurrentEvidenceSatisfied` and cannot satisfy
current-candidate, independent-review, acceptance or deployment gates.

A server-written `contextSnapshot.sourceReferenceUsage` receipt records the
lookup status, number of reference targets and snippets, and zero blob reads
and refreshes. That records preparation of the reference context; it does not
claim the model understood every file or actually relied on every snippet.
Recovery retains the saved execution input and does not perform a new lookup.
No task/session reassignment, session reset, budget reset or retry is added.

For UI development, keep design requirements in the existing trusted agent/task
instructions. For projects that use UI UX Pro Max and Impeccable, require both
workflows, inspect the rendered interface before editing, and retain sanitized before/after
screenshots and a video of the relevant desktop/mobile journey. Use the
existing task evidence/attachment system and independent review. A backend-only
reference change does not establish browser acceptance or justify fabricated
UI evidence.
