---
title: Bind native review to a source candidate
description: Optional candidate SHA on the existing native task review API, with isolated Bruno examples.
---

`PATCH /api/issues/:id` accepts an optional `reviewRequest.candidateSha`
alongside the existing required `reviewRequest.instructions`. This adds a field
to the native task API; it creates no new route or review workflow.

This is a schema example, not permission to mutate a live task. The disposable
fixture below is the only environment described here.

```json
{
  "status": "in_review",
  "comment": "Review the exact candidate and its complete diff and evidence.",
  "reviewRequest": {
    "instructions": "Review the full candidate against the agreed base.",
    "candidateSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}
```

The example SHA is a placeholder; use the full actual candidate commit. The
optional field must match `^[a-f0-9]{40}$`: exactly 40 lowercase hexadecimal
characters. Branch names, abbreviated SHAs, uppercase text and JSON null are
invalid. Malformed values return HTTP 400 with the validation path
`reviewRequest.candidateSha`. Normal authorization, company access, checkout,
review-stage transition and audit rules still apply. Do not send assignee or
execution-stage overrides.

For a configured bound task, the server captures clean final HEAD under the
writer's task, run and workspace leases in the same transaction as the review
transition. Omitting `candidateSha` allows that server capture; supplying it only
narrows capture and returns a conflict if it differs from observed HEAD. A client
SHA never creates a trusted receipt. Board/user transitions without an eligible
writer run refuse with `writer_missing`; they cannot manufacture writer authority.

The server persists `executionState.sourceReviewCapture` and
`executionState.reviewRequest.candidateSha`. Heartbeat derives `reviewCandidateSha`
only for the assigned pending reviewer and matching task/workspace/binding/stage.
Consecutive review stages carry the original receipt and candidate forward when
no writer handoff occurred; they do not recapture reviewer-time HEAD. A return to
the writer requires a fresh writer-owned capture on its next review handoff.
A configured bound review without a matching receipt fails closed. This is source
identity, never permission to execute, accept work or activate indexing.

Capture is owned by `server/src/services/workspace-source-inspection.ts` and
`source-review-handoff.ts`; persistence by `issues.ts`. The request contract lives
in `packages/shared/src/validators/issue.ts` and `types/issue.ts`; heartbeat consumes
it through `server/src/services/heartbeat/source-memory-run-state.ts`.

## Compatibility and mixed-version order

Existing requests with only `reviewRequest.instructions` remain valid at the API
schema level. For configured bound tasks they use server capture under the same writer leases;
otherwise they do not acquire current-source evidence standing. Old saved results and sessions
remain intact; never infer a candidate from a branch, baseRef or arbitrary context.

Upgrade the server schema and native candidate producer before clients send the
new field. A server without this strict-schema addition rejects the unknown
property. Until then, use only the supported `reviewRequest.instructions` and
include the full candidate SHA, whole-diff link and evidence links there. This
text supports manual review; it does not implement the new typed source binding.
Never resend a rejected mutation automatically.

Keep indexing disabled during an approved cutover, quiesce older workers and drain
their transactions before compatible workers touch retained provenance. Older
pruning workers are not safe rollback targets for retained ledgers. These examples
authorize no deployment, retention migration, deletion or real indexing.

## Disposable fixture collection

`bruno/source-review-candidate/` is a standalone collection with valid and invalid
requests plus readback. Open that directory as the collection, rather than running
all parent collections. Provision a disposable local instance and fresh synthetic
company/task with a native review stage and a never-executed synthetic participant.
Use no production data, credentials, remote provider access or shared state.

Before creating fixture entities, an authorized fixture operator must start the
existing task drain (`POST /api/instance/task-drain`), confirm it with GET, keep it
active through the fixture, pause the synthetic company, and disable execution.
The collection does not provision entities or start/extend drains. A drain's POST
receipt is not the computed GET status. Verify zero adapter invocations/running
runs separately, then stop the fixture server and clean up its isolated database.
Never drain a real operator instance for this fixture.

Inject these values into the Bruno process without committing an environment file:

| Process variable | Purpose |
| --- | --- |
| `PAPERCLIP_FIXTURE_BASE_URL` | Disposable HTTP loopback origin, with its isolated port |
| `PAPERCLIP_FIXTURE_ISOLATED` | Explicit `true` confirmation of fixture isolation |
| `PAPERCLIP_FIXTURE_COMPANY_ID` | Fresh paused synthetic company |
| `PAPERCLIP_FIXTURE_ISSUE_ID` | Its synthetic task with native review policy |
| `PAPERCLIP_FIXTURE_CANDIDATE_SHA` | Full candidate commit to persist and read back |
| `PAPERCLIP_FIXTURE_TOKEN` | Optional injected fixture credential; omit only for an isolated local-trusted fixture |

Run requests 01–05 once in order. Read active drain and paused company immediately
before mutation; in-memory checks expire after 30 seconds. Expected responses are
GET 200, GET 200, malformed PATCH 400, valid PATCH 200, and persisted GET 200.
The valid mutation must leave a pending review stage retaining the exact SHA.
The guards reduce accidental use; they do not prove isolation or prevent a drain
expiry race. Fixture isolation, a never-executed participant and operator cleanup
remain essential. Stop on failure; no retry or polling loop is supplied.

The collection injects a credential header using `bru.getProcessEnv` and keeps
runtime state only with `bru.setVar`. It has no token environment file, credential
logging, or persistence calls. In Bruno v4, environment/global mutation scripts
persist changes; keep secrets in process injection or supported secret-manager
references, never `bru.setEnvVar` or global/environment setters. See the
[Bruno v4 release guidance](https://www.usebruno.com/v4-release) and
[official JavaScript reference](https://github.com/usebruno/bruno-docs/blob/main/testing/script/javascript-reference.mdx).

## Evidence scope

Actual isolated curl evidence establishes malformed-field rejection, successful
persistence/readback and producer binding from saved native review state, with
zero adapter invocations and cleanup. The reusable Bruno files document those
requests; Bruno runner execution is not claimed. Documentation additions do not
repeat the curl fixture, semantic compiler, Postgres, synthetic or CI checks.
Hosted CI, full Rust rebuild, full UI qualification and live provider dispatch
are separate from this source/API fixture evidence.

### Native Runner attribution

Fresh native Runner tasks use the final selected provider and model after task
overrides, defaults and compatibility selection
when no legacy phase-routing profile exists. The task work mode determines
planning or implementation; a pending review assigned to the current participant determines review, even
when its capture is missing or invalid (which holds the review). Phase-routed tasks retain their selected profile.
This attribution grants no task or repository access. Restart recovery retains
its existing refusal for an unverified old source snapshot, preserves the saved
session and context, and never substitutes a newly edited live model for it.

An interaction-only native review does not itself produce a writer capture. On a
bound source workspace it therefore refuses with `source_memory_review_candidate_missing`
before any source read; artifact-only review workspaces should stay unbound.
Native preparation may ensure an idempotent completion contract and materialize
response inputs before source validation. Neither starts a provider or accepts
work. Model-fallback warnings are published only after source validation succeeds.
